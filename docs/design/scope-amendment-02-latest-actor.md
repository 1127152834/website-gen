# 规则调整 02：资料最后操作人，与网关申请负责人分开

记录日期：2026-10-16（America/Los_Angeles）。本轮用户明确修订，优先于此前“每个客户一个负责人”和“默认创建人负责”的设计。仅更新设计材料，不写应用代码、不删除现存业务记录。

更新日期：2026-10-17。用户已确认每次申请保留一次资料与最后操作人的定稿；第 4 节取代此前的待确认建议。现有图稿的逐页修改项见[静态原型审查](F:/projects/website-gen/docs/design/customer-attribution-ui-audit-2026-10-17.md)。

## 1. 用户已确定的业务规则

- 准备资料阶段不设客户负责人，也不要求员工在手工/批量建档时指定负责人。
- 申请网关时才确定负责人；其职责是跟进申请，不是替整套资料的填写者承担所有录入归因。
- 每个操作应能定位操作人，尤其驾照导入、驾照信息提取/转录与确认、流水上传、EIN 填写等。
- 资料归因只关心当前最后一次修改由谁完成，不需要中间修改过程或资料版本历史。
- 团队共享、人工确认驾照识别、单在办网关、首个有效获批后客户完成等既定业务保持不变。

## 2. 在页面与保存行为中如何表达

### 2.1 字段级，而不是整页级

- FN、LN、驾照号、生日、SSN、电话、邮箱、街道、城市、州、ZIP、EIN 等可独立编辑的字段，各自显示/可查看最后成功录入或修改人及时间。
- 不能只在“个人资料”或“企业资料”整页写一个最后编辑人。员工只改 EIN，不能把企业名称、地址等未改字段都算到他名下。
- 保存成功且字段值实际改变才更新该字段归因；取消、失败、校验不通过、打开查看、复制、原值保存均不刷新最后修改人。
- 首次录入就是该字段当前的最后录入人；清空已有值也属于修改，应留下该空值的最后修改人。仅补充确认而不改值时，确认人属于独立确认信息，不冒充改值。
- 操作人由系统根据登录账号记录，不由员工在表单里随意选择“由谁修改”。个人账号停用不把已有归因变成空白。
- 并发保存只能更新本次实际变更字段；不能用提交整张旧表单的方式覆盖其他人的最新资料或最后修改人。

### 2.2 每一份附件分别归因

- 同类多份文件各自记录当前文件的上传/替换人、最后成功操作及时间，不把整个银行附件区算给最后上传一份文件的人。
- 替换成功后当前文件对应替换人；新文件失败不能更新归因或提前移除旧文件。当前资料不建立旧文件版本列表；已独立保存在申请定稿中的文件不受影响，见第 4 节。
- 从当前资料移除文件后可保留最小“已移除、最后移除人/时间”说明，便于定位该操作；当前资料不保留旧文件恢复入口。这是最后操作标记，不是中间修改流水。已有申请定稿仍可只读查看其当时文件，不属于当前资料的版本回滚。
- 整个客户删除仍按另行确认的规则清理，不以此条为理由建立已删除客户的隐藏副本。

### 2.3 驾照原图、识别和人工确认是不同环节

| 对象/环节 | 应能看到谁 | 不应混淆 |
| --- | --- | --- |
| 当前驾照图片 | 当前文件导入/替换人、时间 | 导入图片不等于核对其内容 |
| 最近一次识别 | 发起识别的员工、来源为 AI 识别、时间 | 不能把 AI 自动产出写成某人手工填写 |
| 识别结果人工确认 | 最近确认人、时间 | 确认与单个字段实际修改分别记录 |
| 正式档案字段 | 该字段最后成功录入/修改人、时间 | 不能让后一次识别覆盖所有已确认字段的归因 |

- 识别候选值未确认前不改变正式档案字段的最后修改人。首次人工确认写入字段时记录实际确认录入人；以后只把实际改动字段更新为对应员工。
- 示例：李敏导入驾照，王芳确认 FN/LN 等提取结果，陈杰后来只改驾照号：当前图片仍显示李敏；未改字段仍显示王芳；驾照号显示陈杰。不存在“整个个人资料都由陈杰填写”。
- 批量操作按每个实际成功的字段/文件记录，不把失败或跳过项一并记成功。
- AI/系统自动执行的其他操作显示真实来源；有人触发则另示触发人，无人触发时不虚构员工身份。最后操作人是事实依据，系统不自动判定某人导致平台拒绝。

## 3. 网关负责人

- 人员归属设计转为针对具体网关申请；准备资料的客户主档不再有默认负责人。
- 开始申请的页面需要明确本次申请负责人。已完成客户后续申请可以有独立的申请负责人，不改写前一次申请的人员信息。
- 申请负责人不自动覆盖任何字段或附件的最后修改人。
- 选择由谁发起、谁可以指定/更改申请负责人，尚未由本次用户说明确定；此前“仅管理员能改客户负责人”不能直接套用到申请负责人。
- 不假定调整申请负责人会自动迁移邮件凭据、改派邮件案件或改变申请状态。

## 4. 已确认：每次申请保留一份申请时点定稿

### 4.1 确认内容与保存边界

- 用户于 2026-10-17 回复“是的，这个记在我们的这个设计里面”，确认每次网关申请独立保留一份当时资料及各项最后操作人，不保存所有中间修改版本。
- 定稿保存当时的字段实际值、所含每份附件的实际内容及其最后成功操作人/时间；保留驾照识别来源与人工确认等已有归因信息。不能只存会随当前档案替换而变化的文件链接。
- 申请记录关联本次平台、申请标识、定稿时间、定稿确认操作人，以及当时申请负责人。确认整套定稿不把所有字段归因改成确认人；负责人也不覆盖材料操作人。
- 定稿只读。之后修改字段、替换或移除当前附件，不回写任何既有申请定稿。后续另一次申请生成自己的定稿，不共用前一次可变资料副本。
- 当前资料仍只保留最新值和最后操作归因；不增加全量资料版本列表、修改差异时间线或一键恢复旧版本功能。原邮件证据及申请办理进度/结果继续保留为业务记录。
- 已有关联定稿时，单文件移除只影响客户当前资料；删除整个客户档案时，关联申请定稿及其附件也应列入删除影响，不借此建立已删除客户的隐藏副本。具体删除权限仍见第 5 节，不在本轮扩权。

### 4.2 页面落点建议，尚未绘制

- 建议在 O-G04“确认开始申请”时，由人工确认本次申请负责人及定稿范围；在系统成功保存申请和定稿后才显示成功。失败不留下“申请已开始但定稿缺失”的成功界面，也不因重试重复建申请。
- 按钮附近明确：“保存本次申请记录及资料定稿；仍需人工向支付平台申请”。系统不自动知道线下真正提交了哪些内容，定稿不等于支付平台收件或申请回执。
- G02 申请详情内提供“申请定稿”只读区域，显示该次字段、附件、归因和定稿时间；进入附件预览时标为“本次申请定稿 · 只读”，没有替换/移除入口。资料页则明确是“当前档案”。不新增顶级材料页。
- 申请中途新增的补件不自动覆盖最初定稿。本轮确认的是一次申请时点记录，并不意味着已记录全部后续实际提交内容；后续补件关联方式待申请/邮件模块细化，不擅自增加多版定稿。
- 申请负责人指定/改派权限仍待确认；未来改派不改写定稿内“当时负责人”，当前负责人在申请记录中另行展示。上述页面布局与交互需后续出图确认，不算本轮已获 UI 批准。

## 5. 需要改画的页面与旧稿处置

- C01 列表与 C02–C05 等档案头部：移除固定“客户负责人”和“我负责的客户”语义；如果显示人员，应明确标为当前申请负责人或资料最后操作人，不能混用。具体列表列设计待重画。
- C11–C14 建档/识别：不添加负责人分配区；显示建档、图片导入、识别发起和人工确认人员信息。创建人只是事实，不等于负责人。
- C03/C04/C05 查看与编辑：补字段级最后修改人、文件级上传/替换人；日期保持 MM/DD/YYYY，不增加可伪填的操作人字段。
- O-C07–O-C10：保留附件操作主体，补当前文件/最后操作归因；替换与移除文案必须限定“客户当前资料”，说明既有申请定稿不受影响；预览区分当前可管理附件与定稿只读附件。驾照查看页仍只显示上传状态，不恢复缩略图。
- C10 原“操作记录”图不能继续作为全量修改流水扩展；拟改为“资料操作归属”，汇总当前字段/文件最后操作人，而非中间修改过程。申请过程记录仍放在申请业务内。新布局待设计，不算已确认成稿。
- O-C06 原“客户负责人调整”用途废止；不再从客户头部或建档流程进入。原编号暂作为待重规划追踪项，是否用于申请负责人调整需先确认权限/需求，不默认新增该功能。
- O-G04/G02/G01：补具体申请负责人设置/展示；在开始申请与申请详情中落实已确认的定稿规则，同时保留资料各自归因。
- O-C15/O-C16 删除：管理员原有删除权限保留；旧“客户负责人”授权失去对象。准备期其他员工能否删除、申请期是否允许申请负责人删除，另行确认，不能把最后修改人自动当成有权删除客户的人。
- 所有旧 PNG 保留原字节作为过程材料，不冒称已经重画；C10 v1 与 O-C06 v1 从当前候选图册移至历史链接。其他旧图的人员相关部分均需按本次新规则修订。
- 原 133 项清单仍是基线，C06 取消后的 132 个编号是范围追踪数。此次不凭空新增/删除编号，O-C06 标记待重规划，不等于其旧客户改派功能仍有效；后续确认用途再变更分组。

## 6. 交付边界

本轮只有规则确认、静态原型审查、受影响页面标记、备份和哈希核验；没有生成新图，没有改应用代码，没有删除数据，也没有验证真实系统的人员记录或定稿保存能力。
