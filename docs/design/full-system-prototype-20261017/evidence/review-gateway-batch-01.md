# 网关首批静态原型独立视觉审核

日期：10/17/2026（America/Los_Angeles）  
审阅对象：`screens/G01-v1.png`、`screens/G02-v1.png`。  
风格基准：`docs/design/group-03-website-management/W03-site-configuration-v1.png` 与 `prompts/common-style.txt`。  
业务基准：`prompts/gateway-scenes.json` 的 G01/G02、`plans/gateway-demo-data.md`、`plans/shared-mail-evidence.md`。

**结论：v1 暂不通过静态定稿。应完成下列最小修正后再复核；两图均不得作为后续网关图的最终视觉基底。**根任务已在修图，本审阅不修改图片、不生成后续图、不改提示词或主索引。

## 1. G01：全局工作台被画成单个客户入口

### 必改 G01-1：全局身份与开始申请作用域矛盾

- 可见事实：页面标题是“网关申请”，但下方整块 Alex Morgan / C001 顶卡带“开始申请”按钮；Alex 已有 PayPal APP-002 待补件。
- 风险：按钮视觉上属于 Alex，形成在其已有在办时还能再开申请的暗示；全局工作台又被误画成客户档案页。
- 最小修正：移除客户专属顶卡；开始申请移到全局页头，并明确“选择客户后开始”。Alex 的客户已完成状态可放到相关行的次要信息，不作为全局页头。
- 入口不能变成对 Alex 已启用的再次申请，也不能将普通全局按钮整体禁用而妨碍其他客户。

### 必改 G01-2：申请负责人筛选缺失

- 可见事实：现有搜索、支付平台和申请状态控件，以及全部/在办/已结束；没有申请负责人筛选。
- 最小修正：增加“申请负责人”筛选；为避免堆叠，可整理状态下拉和状态分段的重复语义，保留主要筛选结构，不再新建筛选页。

### 必改 G01-3：状态来源不是支付平台名称的重复分类

- 可见事实：两条申请的“状态来源”都写“支付平台”。
- 风险：不能区分人工确认与邮件 AI 更新，来源归因不完整；与平台列冗余。
- 最小修正：APP-001 写“人工确认”；APP-002 写“邮件 AI”。保留原申请负责人王芳/李敏，不把来源字段改成负责人。
- 更新时间保持 APP-001：10/12/2026 14:20；APP-002：10/17/2026 09:20，表头 PT 已覆盖两行。

### 可选 G01-4：搜索提示更符合全局查找

现占位只有“搜索申请编号或支付平台”。建议改成“搜索客户、企业或申请编号”，已有平台下拉仍可筛平台。此项是低成本可用性优化，不要求扩充新的全文搜索能力。

## 2. G02：申请详情的对象、证据与信息结构

### 必改 G02-1：主对象应为 PayPal APP-002

- 可见事实：页面大标题为 Alex Morgan，面包屑为“客户 / Alex Morgan / 网关申请”，但有返回全局网关列表入口、侧栏网关申请选中。
- 风险：用户无法分清正在浏览客户档案还是某次申请；后续同一客户多个历史申请会更容易混淆。
- 最小修正：大标题“PayPal · APP-002”，面包屑从全局网关申请进入；Alex Morgan · C001、Northline LLC、northline.example、hello@northline.example 作为关联身份保留。
- 不新增第二套详情路线；客户档案入口仍打开同一单次申请详情。

### 必改 G02-2：当前状态证据必须来自平台 E-102

- 可见事实：“申请资料与证据”中的邮件证据写“来自客户的原始邮件”，没有明确 E-102 的来源和要求。
- 风险：把平台审核要求误记为客户来信，缺乏当前待补件状态的可核对依据。
- 最小修正：独立来源证据区显示“平台邮件 · E-102 · 10/17/2026 09:20 PT”，主题“Additional statements for APP-002”，保留对应原文查看入口。
- 若显示原文，必须为：`Please provide bank statements for July, August, and September 2026.`
- 不能替换成 E-101 的“最近一期流水＋库存图”。E-101 是 09:18 的另一封邮件。当前来源区是一封当前状态依据，不应暗示全部申请仅有一封历史邮件。

### 必改 G02-3：移除重复申请表，聚焦本次申请

- 可见事实：头部已显示客户完成和 PayPal 待补件；正文又有相关客户状态 Stripe 表，再有当前资料表，最后还有重复 PayPal/Stripe 的历史申请表。
- 风险：同一事实反复出现，当前申请主线被挤到数个表格中；这不是简单的像素问题。
- 最小修正：正文收敛为一块当前申请事实、一块来源证据、一行定稿摘要。保留客户仍完成的简短依据，不再重复整张 Stripe 表或本次 PayPal 行。
- 定稿一行明确“26 项字段 · 9 份附件 · 10/16/2026 14:00 PT”，可进入只读申请定稿。
- 移除“包含营业执照、身份证明、网站信息等”的泛化附件说明，避免把未列入已核定九份附件的“网站信息”画成附件组成。此处无需展开所有分类。
- 现有“人工纠正”“结束本次申请”保留为次级动作；不加开始另一申请主按钮。

### 关联必改 G02-4：不要将负责人当成最新状态操作来源

- 可见事实：重复历史申请表把 APP-002 的 09:20 更新时间与“操作人：李敏”并列；上方同一时点又写“邮件 AI”。
- 风险：可能把自动状态更新错误归到申请负责人名下，不符合最后操作归因。
- 最小修正：删去该重复表即消除这一冲突。保留“申请负责人：李敏”；当前状态更新来源明确“邮件 AI”。若以后显示人工操作人，必须对应其实际人工动作，不从负责人自动推导。
- APP-001 的历史王芳归因保持原样，不换成当前用户管理示例的陈佳。

## 3. 配色与可见可读性

### 必改视觉 V1：G02 普通壳文字过亮蓝

对照 W03，G02 的普通侧栏文字、分组、图标及多处正文标签明显更亮、更饱和，令大量不可操作文字像链接。G01 更接近 W03 的深蓝与灰蓝层级。

- 大标题：近黑海军蓝。
- 普通正文与侧栏：深蓝；辅助标签：灰蓝。
- 明亮蓝仅用于真正的操作链接；不要为每项文本统一套链接色。
- 待补件使用文字和温和橙色状态提示，避免头部红色 PayPal 文案与正文橙色状态形成不同严重程度。
- 保留现有白底、细边框、导航宽度、字号层级和深蓝主按钮，不为修正颜色重排无关区域。

### 当前未发现的额外问题

- 三张可见图的主要中文、英文名称、域名、商业邮箱与申请编号可读，没有发现必须独立返工的明显截断。
- G01 两行申请、共 2 条记录，数据计数一致。
- G02 26 字段、9 附件数值与定稿基准一致；问题在呈现与多余说明，不应随重构更改数字。
- 日期均为美国格式；APP-001 14:20 获批与 09/28/2026 10:00 开始在图上未混同。
- Alex 已完成且 PayPal 待补件并存正确，不应改成未完成。
- 没有独立材料导航、无驾照建档入口、客户固定负责人或平台自动提交成功文案；底部保留人工外部办理边界。

这些结论为静态目视判断，没有做像素颜色值、对比度或 OCR 测量，不声称每个像素完全符合参考。
