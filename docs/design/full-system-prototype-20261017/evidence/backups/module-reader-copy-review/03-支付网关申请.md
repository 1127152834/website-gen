# 支付网关申请

> **设计说明：**本页介绍的是当前一期静态原型，帮助内部员工和管理员理解页面怎么配合使用。图片不可点击，也不代表功能已经上线；真实交互仍需后续验证。

**一句话用途：**集中记录每次支付网关申请的负责人、申请时资料、邮件证据和状态变化，让团队知道当前在办什么、为什么变化，以及客户是否已有有效获批。

## 在整个项目中的位置

这个模块承接客户档案、企业资料、网站和商业邮箱，用于管理外部平台申请过程。**支付网关是连接网站与支付服务的通道，让网站具备收款能力。**申请仍由员工在外部平台人工办理；在本系统点击“开始申请”，只是建立内部申请记录并保存当时资料，不等于已经向外部平台提交。

**资料定稿是开始申请时固定保存的一份资料快照，之后当前客户档案再修改，也不会覆盖这份快照。**当前资料与历史申请定稿分开查看，定稿中可以查阅、复制字段和打开单个附件，但不是一键打包导出。

## 谁用、什么时候用

- **申请经办人：**决定申请平台、开始内部记录，并在外部平台完成实际申请。
- **邮件跟进人员：**把来信关联到正确申请，按原文记录明确要求和处理结果。
- **管理员或复核人员：**纠正误判状态、处理同时开始的冲突、结束申请并核对客户完成状态。

准备资料时没有固定客户负责人；开始某次申请时，才记录该申请的负责人。申请负责人也不会取代各字段和附件的最后操作人。

## 使用前准备

1. 确认客户、企业、网站和商业邮箱关系正确，并核对当前资料是否适合所选平台。
2. 选定外部支付平台和本次申请负责人。
3. 查看 AI 资料审核建议，但把它当作参考。发现问题时可以人工确认后继续；“未发现问题”也不代表平台一定获批。
4. 确认同一客户当前没有另一条申请正在办理。同一时间只能有一条进行中；被拒绝或结束后可以换平台另开一条历史上独立的申请。

## 常用顺序

1. 在全部申请工作台筛选客户、平台、负责人或状态，再选择客户开始申请。
2. 确认平台和申请负责人，保存内部申请记录以及当时的资料定稿。若同时有人已经开始，打开已生效的申请，不要再建第二条。
3. 员工到外部平台人工提交和跟进；本系统不替代这一步，也不提供测试付款或代运营。
4. 在申请详情查看申请时保存的资料，并把相关邮件关联到正确申请。
5. 只按邮件原文记录平台明确提出的要求、日期和处理情况。原文没有写的下一步、所缺月份或截止日期，不自行补充。
6. 邮件 AI 可以依据新邮件推进状态，员工也可以人工纠正。每次变化都要保留来源，避免旧邮件重复处理后覆盖较新的人工决定。
7. 第一条真实有效的获批会把客户标为完成；之后的申请继续单独记录。若唯一的一次获批被纠正为未获批，客户完成状态也要重新计算。
8. 不再办理时结束内部申请。结束不代表远端申请已经撤回，旧邮件再次处理也不能自动重开它。

## 两个具体故事

**故事一：已有一次获批，又申请另一个平台。**Alex 已经有一个有效获批，因此客户状态是“已完成”。后来李敏负责申请另一平台并收到补件邮件。新申请仍单独显示为待补件，但不会把之前的有效获批抹掉，也不会把客户改回未完成。团队只按来信原文记录明确要求，不从附件数量推测平台已经收妥。

**故事二：邮件被误判为获批。**系统把 Casey 收到的“仍在审核”邮件误判成获批，员工核对原文后改回审核中，客户也随之重新变为未完成。稍后收到一封新的明确获批邮件时，新证据可以再次推进申请，并形成首次有效获批与客户完成；旧邮件重放则不会覆盖人工纠正。

## 常见误解与失败处理

- **“开始申请”就是已经提交平台。**不是。它只完成内部记录和资料定稿，远端提交仍由员工人工完成。
- **“当前档案改了，旧申请定稿也会更新。”**不会。两者故意分开，便于说明当时实际使用了什么资料。
- **“一封补件邮件可以推导出完整待办。”**不可以。只记录原文明确表达的要求；邮件原文、AI 建议和人工处理记录要分开。
- **“一次获批后，后续申请会覆盖客户完成状态。”**不会。后续申请独立记录；只有有效获批本身被纠正时，才重新计算客户是否完成。
- **保存结果未知：**先检查申请和资料定稿是否都已保存，再决定下一步；核实前不要重复开始。
- **出现两条可能在办的冲突：**不要自动结束、删除或改派任何一条，先查看两条申请并人工处理冲突。
- **邮件归错申请或分类错误：**保留原文，人工更正归属、分类或处理标记。已结束申请收到旧邮件时只记录，不自动重开。
- **详情部分读取失败：**保留已经看到的客户、申请和状态信息，稍后重试失败区域；不能把“暂时读不到定稿”当成“没有定稿”。
