# 内部用户与权限

> 这里描述原型设计用法，图片不可操作，不代表功能上线。图中的人员、密码和操作结果都是虚构示例；真实账号、权限和会话变化仍需在系统实现后验证。

**一句话用途：**由管理员创建、查找、重置、启用或停用团队内部账号，并在人员离岗时保留既有业务记录。

## 先分清“客户”和“内部用户”

客户把资料交给团队，但不会登录这个系统。“内部用户”是团队工作人员的登录账号，可从左侧导航的“系统”分组进入“用户管理”。

原型只展示两种权限角色：**管理员**和**普通用户**。“运营”是职责备注，说明同事平时做什么，不是第三种权限，也不代表系统还有一套未展示的细分权限。

## 新员工常见任务

| 你要做什么 | 从哪里开始 | 完成后看什么 |
|---|---|---|
| 给新同事开账号 | 管理员进入“用户管理”并选择“创建用户” | 列表中出现该用户名、角色和“必须改密”状态 |
| 新员工第一次登录 | 从登录页输入内部用户名和初始密码 | 必须成功设置新密码后才能进入系统 |
| 同事忘记密码 | 管理员在该用户一行选择“重置密码” | 原有登录全部失效；该用户下次登录必须改密 |
| 同事离岗或暂停访问 | 管理员确认对象后停用 | 用户不能再登录；业务记录仍保留 |
| 同事恢复访问 | 在列表核对当前状态后启用 | 重新读取列表确认状态，不凭旧弹窗判断 |

## 按顺序操作

1. **先找对人。**在[内部用户列表](01-用户管理-内部用户列表.png)按用户名搜索，并结合角色、状态、“必须改密”和创建时间核对对象。不要只看职责备注。
2. **创建账号。**填写用户名、选择管理员或普通用户、补充可选的职责备注并设置初始密码。页面没有规定初始密码如何交给同事，应使用团队认可的安全方式，而不是在公共聊天中发送。
3. **让本人完成首次改密。**创建后，用户用初始密码登录，会进入“首次登录，请修改密码”页面。只有保存新密码成功后才能进入业务页面；退出登录不会替他完成改密。
4. **需要时重置密码。**在[重置用户密码](03-用户管理-重置用户密码.png)中再次确认只读的用户名、角色和职责备注，再输入两遍新初始密码。原型明确显示：重置会让该用户所有已登录会话失效，并要求下次登录立即改密。
5. **离岗时停用，不删除记录。**在[停用确认](04-用户管理-启用或停用用户确认.png)核对当前角色和状态。停用后，该用户不能登录或使用系统功能，但客户记录和历史操作记录仍保留。若他负责某项网关申请，停用不等于交接；当前原型未展示改派负责人入口，应先由管理员协调后续处理，不能假定系统已自动改派。
6. **最后重新核对列表。**静态图只说明预期界面，不能证明点击后已经成功。真实系统中应重新读取列表，以最新状态为准；若提示权限不足、用户已变化或操作失败，先停止重复提交。

## 一个交接故事

管理员林悦为新同事赵宁创建“普通用户”账号，并把“运营”写在职责备注中。赵宁用初始密码登录后，系统要求他先设置自己的新密码；保存成功后才进入工作台。

数月后赵宁离岗，林悦在用户列表确认用户名和当前状态后停用账号。赵宁不能再登录，但他过去填写的客户资料和操作记录没有消失。赵宁原先负责的一项网关申请仍需由管理员协调后续处理；当前原型没有展示负责人改派入口，不能把“账号已停用”当成“交接已完成”。

## 容易误解的地方

- **“客户也在这里开户。”**不是。这里只管理内部员工；客户档案在客户模块。
- **“职责备注就是权限。”**不是。“运营”等文字只帮助团队理解分工。
- **“重置密码只换一串密码。”**不完整。图中同时说明现有登录全部失效，并在下次登录强制改密。
- **“停用等于删除。”**不是。停用只阻止访问，不删除历史记录。
- **“停用会自动转交申请。”**不会。当前原型未展示负责人改派入口，需要先由管理员协调。
- **“看到确认按钮就表示操作完成。”**不是。按钮在静态图片中不可操作；将来使用真实系统时也要以刷新后的列表状态为准。
