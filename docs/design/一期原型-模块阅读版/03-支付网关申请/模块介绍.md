# 支付网关申请

> **设计说明：**本页介绍的是当前一期静态原型，帮助内部员工和管理员理解页面怎么配合使用。图片不可点击，也不代表功能已经上线；真实交互仍需后续验证。

**一句话用途：**集中记录每次支付网关申请的负责人、申请时资料、邮件证据和状态变化，让团队知道当前在办什么、为什么变化，以及客户是否已有有效获批。

## 在整个项目中的位置

这个模块承接客户档案、企业资料、网站和商业邮箱，用于管理外部平台申请过程。**这里的支付网关，指网站收款所申请的支付平台，例如 Stripe 或 PayPal。**申请仍由员工在外部平台人工办理；在本系统点击“开始申请”，只是建立内部申请记录并保存当时资料，不等于已经向外部平台提交。

**资料定稿是开始申请时固定保存的一份资料快照，之后当前客户档案再修改，也不会覆盖这份快照。**当前资料与历史申请定稿分开查看，定稿中可以查阅、复制字段和打开单个附件，但不是一键打包导出。

## 谁用、什么时候用

- **申请经办人：**决定申请平台、开始内部记录，并在外部平台完成实际申请。
- **邮件跟进人员：**把来信关联到正确申请，按原文记录明确要求和处理结果。
- **管理员或复核人员：**纠正误判状态、处理同时开始的冲突、结束申请并核对客户完成状态。

准备资料时没有固定客户负责人；开始某次申请时，才记录该申请的负责人。申请负责人也不会取代各字段和附件的最后操作人。

上述称呼是工作分工，不是新增角色。**当前原型明确展示了“开始申请”时的负责人下拉选择，但没有展开开始后的改派入口及权限。**需要中途交接时先与管理员协调，不要把“人工纠正申请状态”当成改派功能，也不要为了换负责人重复建立申请。

## 使用前准备

1. 确认客户、企业、网站和商业邮箱关系正确，并核对当前资料是否适合所选平台。
2. 选定外部支付平台和本次申请负责人。
3. 查看 AI 资料审核建议，但把它当作参考。发现问题时可以人工确认后继续；“未发现问题”也不代表平台一定获批。
4. 确认同一客户当前没有另一条申请正在办理。同一时间只能有一条进行中；被拒绝或结束后可以换平台另开一条历史上独立的申请。

## 两个入口，先分清查看范围

- **要找团队所有申请：**侧栏“网关申请”进入[申请工作台](01-网关申请-全部申请工作台.png)，搜索客户、企业或申请编号；用平台、申请负责人、状态和“在办／已结束”筛选，再点该行“查看申请”。同一客户出现两行可能是两次不同申请，不一定是重复客户。
- **只处理某位客户：**从客户列表打开完整档案，切到“网关申请”标签。[无在办时](02-客户网关面板-尚无进行中的申请.png)可以“开始新申请”；[已有在办时](03-客户网关面板-已有进行中的申请.png)用“查看申请详情”，不是再开一条。“无在办”不等于从未申请，下面仍可有有效获批和历史记录。

## 第一次开始申请，按这几步走

1. 从该客户的“开始新申请”进入[确认弹窗](05-开始申请-确认平台与申请负责人.png)，先核对客户姓名与编号，再选支付平台、**申请负责人和商业邮箱**。申请标识是可选项。
2. 看“最近材料审核”和“本次申请定稿”预览；附件只显示部分时用“查看全部”。审核未执行或有问题时，可以先去档案的“材料审核”，也可以知情确认后继续，不能把灰色按钮误认为必须审核通过。
3. 勾选保存内部申请记录与资料定稿的确认项；存在未审核风险时，还须勾选相应知情确认，再点 **“保存并开始记录”**。成功应同时有申请记录和资料定稿。若显示“保存结果待核实”，先点[“核实保存结果”](07-开始申请-申请与资料定稿保存结果未知.png)，不要连续重新开始。
4. 负责人再去外部支付平台人工提交。这里保存的是内部准备资料，**不是平台收件回执**；本系统不替代远端申请，也不提供测试付款或代运营。

## 申请开始后，每一页负责什么

在[申请详情](08-申请详情-本次申请概览.png)先核对顶部客户、平台和申请编号，再使用四个标签：

| 页面上的标签 | 什么时候用 | 做完如何判断 |
|---|---|---|
| 概览 | 看本次负责人、商业邮箱、状态来源；通过“打开客户档案”“打开邮箱”交接到对应工作区 | 同时看“客户已完成”和“当前申请”两块，不能混为一个状态 |
| [申请定稿](09-申请详情-查看申请时保存的资料.png) | 查开始时保存的字段、附件及当时操作人；附件可查看、单份下载、翻页 | 只读，不在这里替换新文件；例如显示 4/9 份时，另 5 份在后续页，并非丢失 |
| [邮件与明确要求](11-申请详情-相关邮件与明确要求.png) | 用“查看原邮件”核对证据；“关联邮件”确认归属；“查看要求”看平台具体要求 | 只按原文记录材料、月份、期限；没写的就不猜。上传文件不等于已发送 |
| [状态与纠正记录](15-申请状态-状态变化与纠正记录.png) | 追查状态为何改变、由哪封邮件或哪位员工推动 | 看时间、来源、依据；这是申请状态记录，不是客户所有字段的编辑历史 |

### 收到补件要求时，别停在“已上传”

1. 在“邮件与明确要求”点“查看要求”，打开[明确要求与处理记录](13-申请要求-查看明确要求与处理记录.png)，读来源原文，核对已关联的当前文件。银行流水回客户“银行资料”整理；库存照片、履行协议等在客户“网关申请 → 补充证明”中管理。也可按要求页的“选择文件”上传或关联本项资料。
2. 资料备好后，按平台要求实际提交；需要邮件回复时用“去邮箱回复”，到[邮箱模块](../04-邮箱与邮件跟进/模块介绍.md)核对发件人、附件和内容后发送。旧定稿不会因补充文件而改写。
3. 回来[记录本项处理结果](14-申请要求-记录本次人工处理结果.png)，依据实际情况选择“已发送回复／已完成处理／忽略／受阻”，填写说明及证据。只是回复“正在准备”时，不要记为材料已交齐。保存一项的记录，不会自动完成其他要求，更不代表平台已认可。

### 状态有误、获批或不再继续时

- **发现误判：**从概览点“人工纠正”，在[纠正侧栏](16-申请状态-人工更新或纠正.png)选择目标状态、填理由、核对原文和客户状态变更预览，再“保存纠正”。预览不是已经保存；之后检查状态与纠正记录。新邮件仍可继续推进，旧邮件重复处理不能覆盖人工决定。
- **收到明确获批：**核对对应申请和来源证据，再查看[获批结果](19-申请状态-首次有效获批与客户完成.png)。第一条有效获批使客户完成，后续申请各自记录；唯一获批若被纠正为未获批，客户状态也要重新判断。
- **不再办理：**在概览“结束本次申请”，[填写原因并确认](24-结束申请-结束本次申请确认.png)。保存成功才释放在办名额；定稿和原邮件保留，远端是否撤回仍需另外核实，旧邮件不能自动重开。

## 两个具体故事

**故事一：已有一次获批，又申请另一个平台。**Alex 已经有一个有效获批，因此客户状态是“已完成”。后来李敏负责申请另一平台并收到补件邮件。新申请仍单独显示为待补件，但不会把之前的有效获批抹掉，也不会把客户改回未完成。团队只按来信原文记录明确要求，不从附件数量推测平台已经收妥。

**故事二：收件确认被误判为获批。**Casey 的邮件只说“材料已收到，申请仍在审核”，系统却误判为获批。李敏通过“人工纠正”改回审核中，先看预览中的“客户已完成 → 未完成”，再保存。后来收到一封明确获批的新邮件，新证据才再次推进申请并完成客户；重读那封旧收件确认不会推翻人工纠正。

## 常见误解与失败处理

- **“开始申请”就是已经提交平台。**不是。它只完成内部记录和资料定稿，远端提交仍由员工人工完成。
- **“当前档案改了，旧申请定稿也会更新。”**不会。两者故意分开，便于说明当时实际使用了什么资料。
- **“一封补件邮件可以推导出完整待办。”**不可以。只记录原文明确表达的要求；邮件原文、AI 建议和人工处理记录要分开。
- **“一次获批后，后续申请会覆盖客户完成状态。”**不会。后续申请独立记录；只有有效获批本身被纠正时，才重新计算客户是否完成。
- **保存结果未知：**先检查申请和资料定稿是否都已保存，再决定下一步；核实前不要重复开始。
- **出现两条可能在办的冲突：**不要自动结束、删除或改派任何一条，先查看两条申请并人工处理冲突。
- **邮件归错申请或分类错误：**保留原文，人工更正归属、分类或处理标记。已结束申请收到旧邮件时只记录，不自动重开。
- **详情部分读取失败：**保留已经看到的客户、申请和状态信息，稍后重试失败区域；不能把“暂时读不到定稿”当成“没有定稿”。

**下次回来先看什么？**申请工作台按自己负责的在办申请筛选，打开详情核对最新状态与来源，再到“邮件与明确要求”处理有原文依据的事项。不要仅凭客户“已完成”就忽略后续仍在办的申请。
