状态：访谈共识整理；用于后续页面设计，不是已实现功能清单。

范围：内部业务结构、对象关系、资料范围、状态与操作规则；本版不设计页面、不提供数据库迁移或功能实现。

## 1. 系统定位与业务终点

系统从“网站生成工具”扩展为“内部客户办理与材料管理系统”。客户不登录、不填写系统表单、不查看系统进度；由员工接收资料、录入、办理和跟进。

网站是客户办理过程中的一项业务产物和支付申请材料，不再是全部业务的顶层对象。

- **系统内完成**：该客户第一次获得支付网关批准。
- **系统外实际交付**：接入网关并测试付款成功。此步骤及后续代运营不在本期。
- 获批后仍可继续申请其他网关；后续申请不抹掉此前的真实获批结果。
- AI 误判获批被人工纠正时，必须同步纠正客户完成状态，不能留下错误的“已完成”。

## 2. 术语与对象关系

### 2.1 统一术语

| 术语 | 本系统含义 | 不应混淆为 |
| --- | --- | --- |
| 系统用户 | 管理员或员工 | 美国客户本人 |
| 客户档案 | 一位客户的个人、企业、网站、材料和申请信息的业务入口 | 一个网站、一个登录账号 |
| 整套客户资料 | 客户档案关联的全部当前资料，访谈中的“一个材料” | 单个文件 |
| 材料文件 | 驾照图片、企业文件、流水、介绍信等附件 | 整套客户资料 |
| 网关平台 | Stripe、PayPal、Payking 等申请目标的业务称呼 | 某次申请、获批后的商户账号 |
| 网关申请 | 针对一个平台的一次人工办理记录，可含多封邮件 | 邮箱、单封邮件、平台本身 |
| 材料审核 | AI 对当前资料及网站信息的参考检查 | 平台审批、真实性保证 |
| 邮件预审 | 现有邮件模块对邮件内容和证据的分析 | 材料审核、平台实时状态查询 |
| 客户删除 | 删除客户档案和网站，保留域名、跳过邮箱 | 暂停、归档、现有“放弃站点”操作 |

### 2.2 核心关系

```text
内部团队
├─ 管理员 / 员工
└─ 共享客户档案（每个客户一个负责人）
   ├─ 个人资料与驾照
   ├─ 企业档案（一个）
   ├─ 独立站（一个，含域名关联）
   ├─ 商业邮箱关联（一个，用于平台沟通）
   ├─ 材料分类 → 多个当前材料文件
   ├─ 材料审核任务 / 结果
   └─ 网关申请（多次）
      ├─ 本次目标平台、办理状态和结果
      ├─ 相关邮件、补件要求和待办
      └─ AI 推进证据与人工纠正记录
```

建档初期允许企业、网站、邮箱尚未创建，关系暂为空；业务目标仍是一客户、一企业、一网站、一商业邮箱，不扩展为多企业或多站点产品。

网关关系是一客户对应多次申请，可以有多个已获批结果，但**同时最多一个申请进行中**。设计建议：同平台一次办理已经明确结束后再次申请，另建申请记录，不覆盖上次结果；同一次申请的补件续办不拆成新申请。

现有“批次”继续作为批量建站的执行组织方式，不等于一个客户，不再承载客户完整业务身份。

## 3. 人员、共享与责任

### 3.1 已确认规则

- 团队内共享客户资料；每个客户有一个负责人；管理员可查看全部。
- 客户不接触系统，无客户门户、外部补件表单或客户登录账号。
- 网关申请由负责人手动确认开始，系统不自动在支付平台提交申请。
- 负责人可在未审核、审核失败或存在风险问题时继续申请，系统如实记录，由员工承担办理判断责任。
- 只有该客户负责人或管理员可以删除客户，其他员工不能删除。
- 人工可以纠正邮件 AI 状态；更正不能仅改变显示而不改变关联业务状态。

### 3.2 页面设计用的默认建议（不冒充已单独确认的权限细则）

- 日常录入、补件、纠错按内部共享协作处理，不新增部门权限层级。
- 新建客户默认由创建员工负责；管理员可调整负责人。
- 共享的是业务资料，不等于开放员工个人模型密钥或任意跨工作区写入权限。
- 业务数据应具有团队共享边界和稳定归属，不能继续把员工登录账号直接等同于客户数据的所有权。

## 4. 资料结构与来源

允许先建立不完整草稿。下表列明应管理的信息，不把所有字段都变成创建客户的硬性必填项。

### 4.1 个人与驾照资料

| 信息 | 来源与规则 |
| --- | --- |
| 名 FN、姓 LN | 驾照正面识别，员工确认，可手工纠正 |
| 生日 | 驾照识别或手工录入，员工确认 |
| 驾照号码 | 正面识别，员工确认 |
| 驾照地址 | 正面识别；保留为证件记载地址 |
| 当前居住地址及邮编 | 客户另行提供，员工录入；不被驾照识别结果自动覆盖 |
| 驾照签发/生效日期 | 可选；能识别则填入，不能识别不猜测 |
| 驾照到期日期 | 识别或手工录入并确认 |
| 驾照正面照片 | 批量识别建档的原始材料；手工建档后也可补传 |
| 驾照反面照片 | 可选，工作人员后续手动上传，本期不通过反面识别建档 |
| SSN | 客户提供，员工录入，不从驾照内容推断 |
| 个人电话、个人邮箱 | 客户提供，员工录入 |
| 信誉分 | 可选，客户提供或员工录入；不由 AI 凭空推断 |

“驾照地址”和“当前居住地址”不同，本身不是材料矛盾或审核失败。识别原文和员工确认的当前字段需要区分，后续重复识别不能悄悄覆盖已确认数据。

### 4.2 企业资料

- 企业法定名称。
- 售卖商品品类及细分类目意愿，例如男士服装、家具、文具、圆珠笔、男士背心等。
- 企业地址，独立于客户两种个人地址。
- 企业外部办理状态及必要说明。
- 企业章程/成立文件。
- EIN 号码；相关证明文件如有则归档，不额外把未确认过的文件种类设为硬门槛。

企业申请在系统外办理，系统只记录状态和结果。企业资料与 EIN 齐备，是开始新建网站的已确认前提。

### 4.3 银行与其他证明材料

- 公户银行信息、银行介绍信。
- 公户账号、routing 号。
- 近三个月银行流水/对账单，允许合并文件或多份文件。
- 履行协议、库存照片及其他补充证明。

全部由客户提供、员工录入上传；本期不办理银行开户。证明材料不作为全客户统一必填项，材料多不等于必须全部向每个平台提交。

同类可有多个文件。除驾照等常用分类外，允许记录其他证明材料类别，避免后续出现新文件类型就无法归档。

某项通用可选材料若被当前平台明确要求补交，应成为本次申请的待办，而不是把该材料改为所有客户的永久必填项。负责人仍有人工办理决定权。

### 4.4 网站、域名与商业邮箱

| 网站公开信息 | 事实来源 |
| --- | --- |
| 企业法定名称 | 企业档案 |
| 企业地址 | 企业档案 |
| 联系邮箱 | 该客户商业邮箱 |
| 联系电话 | 客户个人电话 |
| 店铺品牌名 | 单独录入，可不同于企业法定名称 |
| 商品与铺货方向 | 客户经营意愿、企业品类及现有铺货/建站能力 |

保留域名、站点和商业邮箱的关联；个人邮箱与商业邮箱不能混用。网站公开信息不自动使用驾照地址或个人当前住址。

新站从客户档案带入资料，复用现有建站和铺货能力。已有网站可人工关联客户，不要求重建，也不因为关联成功就伪造“企业资料已齐”或“网站已重新验收”。

资料修改不等于线上网站已经更新；需要区分档案当前值、网站当前可见值及待同步差异。

## 5. 建档、重复提示与材料生命周期

### 5.1 批量驾照建档

1. 批量上传，默认每张都是驾照正面，不自动把图片当作反面配对。
2. 逐张识别并生成待确认草稿；失败的单张保留失败状态，不能把整批标成全部识别成功。
3. 显示识别字段、缺失或不清晰项，员工确认/纠错。
4. 对重复图片、已存在的驾照身份线索、同名客户提供提示。
5. 员工决定关联已有客户、确认为新客户或跳过；不能因同名自动合并或拒绝建档。
6. 确认后形成客户档案，继续补充 SSN、现住址、电话、邮箱等资料。

手工建档与批量建档汇入同一客户模型。识别失败不阻止手工填写，也不代表身份验证失败。

### 5.2 文件规则

- 同类多文件；支持补传、替换、移除。
- 替换直接更新当前材料，不增加文件版本列表，不偷偷保存旧附件作为“历史材料”。
- 保留当前文件类型、所属客户、上传人和时间等必要管理信息。
- 旧审核结果可标为失效，但不能再把被替换材料的检查结论当成当前结论；不承诺旧原件可回放。
- 员工通过档案复制字段、按需打开或下载单个文件；不提供打包导出流程。
- 不做表格导入。Grist 未来可作为最终汇总目标，但同步、字段映射和自动导出均不属于已确认的一期范围。

## 6. 办理流程与状态分层

### 6.1 常规业务路径

```text
驾照/手工建档 → 补充个人和企业资料
                         ↓
               系统外申请企业 → 录入企业文件和 EIN
                         ↓
               域名 / 商业邮箱 / 网站与铺货
                         ↓
               资料准备 + AI 参考审核
                         ↓
               负责人确认开始网关申请
                         ↓
               邮件跟进 ↔ 补件 / 增量检查 / 人工纠错
                         ↓
                 首次获批 → 客户完成
                         ↓
                 可继续追加新的网关申请
```

这是一条常规路径，不是一张“缺任意资料就锁死”的强制流程表。材料随时可补，AI 审核可跳过；新建站的企业就绪条件、负责人确认开始以及单在办限制则必须保留。

### 6.2 不用一个状态承担所有含义

| 层次 | 记录什么 | 不能被什么替代 |
| --- | --- | --- |
| 客户完成状态 | 尚未完成 / 已完成及首次有效获批时间 | 网站建成、审核有分数、邮件已读 |
| 企业办理状态 | 未申请 / 办理中 / 待补充 / 已办结（建议命名）；另判断企业资料与 EIN 是否齐备 | 仅填了企业名称 |
| 网站状态 | 已有站关联或现有建站流水线真实进度、失败和结果 | 已创建客户、已获批网关 |
| 当前网关申请 | 当前目标、办理状态、补件和结果 | 客户主状态 |
| 材料审核状态 | 未审核、进行中、完成、失败、部分完成、需更新 | 平台审批结果 |

客户整体办理进度可以由这些事实归纳，不额外引入用户拒绝的“暂停/归档”业务线。

## 7. 网关申请与客户完成规则

### 7.1 申请状态语义

| 状态 | 占用唯一在办名额 | 含义 |
| --- | --- | --- |
| 未开始 | 否 | 尚未由负责人确认开始 |
| 申请中 / 审核中 | 是 | 已开始本次外部人工申请 |
| 待补材料 | 是 | 当前申请需要补充材料 |
| 等待平台回复 | 是 | 本次申请尚无明确最终结果 |
| 已获批 | 否 | 本次申请得到批准 |
| 已拒绝 | 否 | 有明确拒绝结果，而不是普通风险提示 |
| 已撤回 / 已终止 | 否 | 负责人确认已结束本次办理，记录原因 |

表内是业务语义，不要求直接替换现有邮件模块的所有分类和待办状态。

负责人开始申请时明确本次目标平台；开始动作只记录人工外部办理，不进行平台自动提交。并发限制必须对所有共享员工生效，不能只靠某个页面禁用按钮。

长期无回复不能自动当作拒绝或终止。新申请开始前，上一申请必须明确结束；系统改状态并不代表平台端已收到撤回申请。

### 7.2 完成与纠错

- 存在至少一次未被纠正为误判的获批结果，客户即完成。
- 首次有效获批确定首次完成时间；追加申请进行中或被拒不会把客户改回未完成。
- 唯一获批结果被纠正为误判后，客户恢复未完成；若另有有效获批结果，则仍完成并依据其结果校正完成时间。
- 真实获批后的账户经营、风控或注销不属于本期代运营流程；不要与“原获批记录是误判”的纠错混为一谈。

### 7.3 一致性补充建议

若 A 被误判获批后已开始 B，随后人工纠正 A，可能出现真实在办归属冲突。必须保留纠错事实、同步修正客户完成状态，并交负责人确认；不能为了维持“单在办”的显示而删除 B 或伪造 A 的终止。冲突未处理期间不得开始第三次申请。

此项是异常一致性的设计建议，具体冲突处置交互留到后续设计，不声称平台端永远不会出现并发。

## 8. AI 材料审核：参考工具，不是审批闸门

### 8.1 一期检查范围

1. 信息完整性：缺哪些当前办理所需的信息，区分通用可选项和本次已知要求。
2. 材料一致性：姓名、企业名称、EIN、相关地址等是否出现无法解释的冲突。
3. 明显问题：无法辨认、图片模糊、证件日期异常或过期等。
4. 网站一致性：网站公开企业名称、地址、邮箱、电话与档案是否一致。

报告说明检查范围、完成情况、问题及证据、建议、时间。报告中的“无发现”只适用于实际检查过的范围，不能覆盖未读取、不可访问或执行失败的部分。

一期不做深度评分系统，不保证文件真实性，不保证平台批准。允许使用系统配置的 AI 服务处理资料。

### 8.2 人工决定权

- 未审核、审核中、审核失败、存在高风险问题，均不阻止负责人手动开始申请。
- 可以提示并记录负责人已经知悉，但不能把提示变成未经确认的强制修复门槛。
- 员工接受风险不等于审核通过；AI 服务失败也不等于材料有问题。
- 后续深化审核不会默认改变本期“工具供人参考”的定位；若要改变必须另行确认。

### 8.3 增量检查

- 首次检查覆盖本次选择的当前资料；后续只检查变化内容及依赖它的一致性项目。
- 修改企业地址，要重查企业与网站地址一致性，不重读所有未变驾照或银行原件。
- 替换流水，重查新流水及涉及其所属人/企业等关联项；不重复其他无关检查。
- 换网关，复用仍有效的通用检查，补查已知平台差异。没有明确依据的特殊要求标为未核实，不能编造。
- 结果要区分仍有效、需更新、未检查；不能把旧报告整体继续标为当前全部通过。
- 增量审核不是材料版本管理，不要求保存被替换附件的历史副本。

### 8.4 数据处理边界

用户接受由已配置 AI 服务处理资料，并明确不要求为 SSN 增加加密操作。本版不擅自增加这项产品门槛，也不修改现有邮箱/API 凭据的安全机制；不将“内部使用”描述为没有泄露风险。

仅向模型提供任务需要的资料、避免在通用日志中输出原文，属于后续技术方案建议，不是已实现声明。所有真实证件和账号均应留在业务系统，本设计文档不包含真实客户数据。

## 9. 邮件 AI 与申请联动

1. 商业邮箱用于与支付平台沟通，同一邮箱可能先后承载多个平台或多次申请。
2. 邮件要关联到具体申请，不能仅凭“来自这个邮箱”就更新该客户当前申请。
3. AI 可根据明确邮件证据自动更新，包括获批和拒绝；这是系统记录的业务判断，不是对平台 API 的实时核验。
4. 记录支持状态变化的邮件/事件与理由，区分局部里程碑、待办完成和整项申请获批。
5. 人工纠正保留操作依据；同一旧邮件重放不能覆盖纠正，新邮件可以提供新证据继续推进。
6. 不为了自动化强行归属或宣布获批；设计建议是将归属不清、证据不足或相互矛盾的项目交人工待确认，具体组织形式留到页面设计。
7. 已明确撤回/终止的申请不被后来的旧邮件自动重开；客户删除后也不能被邮件自动复活。
8. 邮件中要求补件形成申请待办，上传文件本身不等于已经向平台提交；系统不自动发信或申请。

## 10. 客户删除：档案和网站删除，域名保留，邮箱不处理

### 10.1 已确认删除范围

| 对象 | 处理 |
| --- | --- |
| 客户记录、个人字段、企业资料 | 删除 |
| 驾照和其他材料附件 | 删除 |
| 材料审核报告、客户侧网关申请记录、客户专属待办与关联记录 | 删除，且不能作为隐藏客户副本继续使用 |
| 关联网站 | 删除实际网站及相应本地站点信息，不只是隐藏或解除客户关联 |
| 域名 | 与网站解除关联，域名本身保留；不注销，不擅自关闭续费 |
| 商业邮箱及其原邮件 | 不处理；不删除邮箱、不关闭邮箱续费、不清空邮件 |

只有客户负责人和管理员可执行。有进行中的申请时，必须确认负责人已经线下结束或决定不再跟进，不把删除伪装成平台已撤回。删除安全设计建议：所有删除均展示客户和影响范围并二次确认。

保留邮箱意味着邮件中可能仍有客户资料。这里的“删除完整客户档案”不等于“所有系统、外部平台、历史备份中的相关信息已经清零”。

### 10.2 执行可靠性建议

这些是后续实现需要保证的执行规则，不增加暂停、归档或回收站业务功能：

- 删除前重新确认网站归属、域名绑定和当前负责人；关联不唯一时不得猜测目标。
- 阻止待完成的识别、审核、邮件任务继续向删除中的客户回写；已删除客户不能被后台任务重新创建。
- 不为解绑网站误删邮箱相关配置；域名与邮箱的购买/续费状态保持不变。
- 外部网站删除、域名解绑、本地档案清理分别记录执行与核验结果；失败或未知就显示失败/待核验，不能宣布全删成功。
- 清理顺序与重试应保留必要的非敏感操作定位信息，防止先丢掉远端资源标识而无法继续清理。
- 最小删除操作记录仅用于执行核验、防止重复操作和旧任务回写，不保留被删客户的个人字段、材料或完整申请历史作为“归档”。
- 删除远端网站不承诺可回滚；代码回滚也不会恢复已经删除的远端资源。

## 12. 一期边界与后续方向

### 一期业务范围

- 共享客户档案、负责人、个人与企业资料。
- 批量正面驾照识别、人工确认、重复提示、手工建档。
- 多文件材料管理、直接替换、文件分类及单项访问。
- 企业外部办理状态与结果记录。
- 企业就绪后衔接现有域名、邮箱、建站与铺货；关联已有网站。
- 简单、可绕过的 AI 参考审核及增量检查。
- 多次网关申请、唯一在办、邮件 AI 联动和人工纠错。
- 首次获批完成及误判纠正联动。
- 按上述权限和资源边界删除客户。

### 不纳入本期

- 客户门户、客户自助提交、客户直接补件。
- 企业注册、银行开户、支付网关自动申请。
- 网关接入配置、测试付款、后续代运营。
- Grist/Excel 历史表格导入、打包导出、材料版本管理。
- 客户暂停/归档流程。
- 深度材料评分、真实性保证或获批承诺。
- Grist 最终汇总的自动同步。

## 13. 业务一致性复盘与后续验收场景

本表是设计检查及未来验收清单，不是已运行的软件测试结果。

| 场景 | 必须得到的业务结果 |
| --- | --- |
| 批量中一张图片识别失败 | 该张待人工处理，其他识别结果不丢；不能称全批成功 |
| 同名、重复驾照或重复图片 | 提示员工决定，不自动合并或覆盖已确认客户 |
| 驾照地址与现住址不同 | 分别保留，不自动判为冲突或公开到网站 |
| 企业文件有了但 EIN 未齐 | 不开始新建站；允许继续补资料 |
| 关联已有网站 | 保留原站点，不重建，不伪造已完成其他步骤 |
| AI 未运行、失败或提出高风险问题 | 负责人仍可确认开始申请，审核状态保持真实 |
| 修改企业地址 | 只更新相关检查，包括网站地址一致性，不全量重读其他资料 |
| 替换一份流水 | 当前文件替换，不保留材料版本；原相关审核不再冒充有效 |
| 两名员工同时开始不同网关申请 | 正常启动入口只允许一个生效 |
| 当前申请待补件 | 仍占在办名额；补传不等于已对外提交 |
| A 明确拒绝/终止后申请 B | A 的结果保留，B 独立记录；不会覆盖为同一次申请 |
| A 获批后申请 B | 客户保持完成；B 独立显示，B 被拒不撤销 A |
| 唯一获批被人工纠正为误判 | 客户同步变为未完成；另有真实获批则仍完成 |
| 同一旧邮件重复处理 | 不覆盖人工纠正；新邮件仍可提供新证据 |
| 邮件归属不清 | 不推进错误客户或错误申请，交人工确认 |
| 非负责人且非管理员尝试删除 | 不允许执行 |
| 有在办申请时删除 | 先明确确认，不声称已经向平台撤回 |
| 删除成功 | 档案与网站删除，域名解绑但保留，邮箱不处理 |
| 远端删除失败或结果未知 | 记录实际完成项和剩余项，不宣称全部成功 |
| 删除后收到旧邮件或迟到任务 | 邮箱照常保留，但客户和已结束申请不被自动复活 |

## 14. 下一步：页面设计输入

业务结构的中心已经确定为“客户档案”，其下关联企业、材料、网站、邮箱和多次网关申请。

下一步才决定这些对象如何组织为导航、列表、详情、批量确认和操作入口；不在本版预先固定页面数量或布局。

进入页面设计时继续保留三个区分：客户是否完成不等于当前申请是否在办；材料审核结果不等于申请许可；删除客户档案不等于注销域名或删除邮箱。
